# I6：上下文工程概述

> Easy Data x AI 课程 · 产业应用篇 · 第 6 节

在新会话中继续一个项目，Agent 需要找回已经确认的决定，并判断它们是否仍然有效。本节用订单日报任务说明如何管理这些上下文，并以 PowerContext 为例，完成工具接入、记忆保存、跨会话检索和修订练习。实操选用 Codex 演示，你也可以使用支持相应扩展机制的其他 Agent 工具。开始前，你需要有使用 Agent 的经验，并能执行基本的命令行操作。

## 学习目标

学完本节，你将能够：

1. 解释扩大上下文窗口为什么不能自动提高有效信息密度。
2. 区分来源、记忆、任务状态、上下文准备和交接，并说明 PowerContext 如何组织这些信息。
3. 根据当前任务选择上下文，控制输入大小，并通过引用核对内容版本。
4. 说明 MCP、Skills、Agent Plugins 各自的作用，并通过插件接入上下文管理工具。
5. 保存一条 Memory，在新会话中找回它，修订后读到新旧两个版本。
6. 检查上下文是否进入请求、是否被采用，以及它对任务质量、延迟和成本的影响。

## 1. 从上下文窗口到上下文管理

### 1.1 窗口容量解决不了信息选择

扩大上下文窗口能装入更多 Token，但不能自动提高有效信息密度。把更多材料放进请求时，重复、过期或互相矛盾的信息也可能随之进入。处理这些输入通常还会增加费用和等待时间，具体开销取决于模型、缓存和服务实现。

假设你正在用 Agent 开发订单日报。一份需求文档规定统计最近 7 天的退款，后来的评审将范围改为最近 14 天，聊天记录中还保留着最初的方案。即使这些材料都能放进窗口，Agent 仍需判断该采用哪条决定，并找到修改依据。

提示词工程帮助你把任务和约束说清楚。上下文工程还要解决材料如何进入请求的问题：哪些内容值得保存，何时读取，一次提供多少，出现冲突后怎样处理。工作需要跨会话继续时，就要在会话之外保存这些信息，并维护它们的状态。

### 1.2 工作越长，越需要保留已确认的信息

Agent 可以辅助完成一个步骤，也可以连续执行工作流，或与其他 Agent 分工合作。参与的步骤越多，需要参考的材料往往也越分散：需求在工单里，修改在代码仓库里，讨论和检查结果又保存在别处。接手任务时，Agent 需要重新找到这些信息。

订单日报任务换到新会话后，接手者可能只知道要生成报表，却不知道统计口径已经改过，也不清楚哪些检查已完成。重新读完整段对话很费时，还可能把讨论中的设想当成最终决定。

如果把当前决定、检查结果和待办事项保存在项目中，下一位参与者就有了明确的起点。即使换了人、Agent 或模型，也能先找到这些记录，核对当前状态后继续工作。

### 1.3 每次请求需要一个合适的视图

资料少时，把它们写进固定提示词很方便。随着项目推进，这种做法会越来越难维护：新旧规范混在一起，每次都要判断哪些仍然适用，也要检查剩余窗口是否足够完成任务。

一次请求通常只需要项目资料中的一部分，我们把这部分内容称为本次请求的视图。核对退款口径时，需要当前决定及其依据；排查报表生成失败时，则需要相关报错和代码。两个请求属于同一项目，所需材料却不同。

准备视图时，先确认任务必需的事实和约束，再去掉无关内容，并保留关键依据的出处。长期存储负责保存资料，上下文准备负责选择本次要用的部分。输入短一些可以减少开销，但漏掉退款口径这样的关键约束，会直接影响结果。

## 2. 上下文中的数据职责与对象模型

### 2.1 五类数据职责

订单日报任务中的信息用途各不相同，可以分成以下几类：

| 数据职责 | 需要回答的问题 | 订单日报中的内容 |
| --- | --- | --- |
| 来源 | 这条信息来自哪里，有什么证据 | 需求文档、评审意见、检查输出 |
| 记忆 | 哪些结论值得在后续请求中复用 | 退款统计范围已经确定为 14 天 |
| 任务状态 | 工作推进到了哪里 | 查询已写好，结果尚未与样本核对 |
| 上下文准备 | 本次请求需要看到哪些内容 | 核对统计口径所需的当前决定和引用 |
| 交接 | 接手者需要知道什么才能继续 | 当前目标、已完成检查、缺口和下一步 |

来源保留证据，记忆保存以后还要用的结论。例如，完整的评审对话可以作为来源，而其中确认的退款范围适合保存为记忆。决定改变或不再适用时，需要修订或停用这条记忆。

记忆的提取、保存和召回实现，可以参阅[《Agent 开发与记忆系统》](../dev/D4%20课程稿：Agent%20开发与记忆系统.md)。

任务状态记录当前进度。把工作交给别人时，还要说明检查过什么、结果在哪里、哪些问题尚未解决，这些内容共同构成交接。任务完成后，当时的进度可以归档，后续仍要遵循的决定和可复用经验则继续保留。

这些分类帮助我们判断一条信息该如何使用。具体到 PowerContext，来源由 Source 表示，记忆和交接属于 Artifact，上下文准备生成临时视图；Trigger 决定何时进行相应处理。任务状态可以记录在来源中，也可以整理进交接产物。

### 2.2 Source、Artifact 和 Trigger

PowerContext 用三个概念组织上下文：Source 提供材料，Artifact 保存整理后的产物，Trigger 决定处理动作。

| 概念 | 职责 | 订单日报中的例子 |
| --- | --- | --- |
| Source（来源） | 保存工作材料，或记录外部材料的引用 | 需求文档、用户纠正、检查结果 |
| Artifact（产物） | 保存后续工作可以使用的内容，并保留版本 | 当前统计口径、任务交接、可复用经验 |
| Trigger（触发器） | 根据收到的信号和当前状态，决定需要进行的处理 | 有新来源时确定处理范围，收到交接信号时推进交接状态 |

三者的关系是 `source → artifact ← trigger`。两条箭头分别表示证据和控制：Source 为产物提供依据，Trigger 决定产物如何生成、更新或使用。

保存一条 Source 后，系统有了可查的材料。是否从中提炼记忆，还取决于配置的处理规则。例如，一次讨论可能包含多个尚未确定的方案，适合先保留原始记录，等决定明确后再保存为记忆。

Artifact 按用途分为不同类型。Memory 保存事实和约束，Handoff 记录交接时的目标与进度，Experience 总结经过结果验证的经验，Skill 提供可复用的操作方法。它们需要的审核和分发步骤也有所不同。

Trigger 根据收到的信号和当前状态，给出新的状态及待执行动作，再由 PowerContext 的运行时执行。例如，发现新增来源后，Trigger 可以选出下一批要处理的材料；如何读取材料、是否调用模型，则由后续处理逻辑完成。

### 2.3 用 Scope 保留工作范围

Scope 表示一组上下文所属的工作范围，`scope_id` 是它的标识。例如，为 Aurora 订单日报创建一个 Scope 后，今天和明天的会话都可以访问它。Session 表示一次会话；会话结束后，Scope 中保存的内容仍然存在。

PowerContext Server 负责生成 Scope ID。项目目录和会话可以绑定到这个 ID，方便以后找到同一组资料。需要独立保存另一个项目时，应创建或选择对应的 Scope；仅切换目录不一定会隔离数据。

使用 Scope 时，还要检查访问权限。Scope ID 用于选择资料范围，服务端另行判断调用者是否有权读取或修改其中的内容。

### 2.4 长期产物和本次视图

PowerContext 根据当前请求选择内容、限制输出大小，并附上引用，得到 `PreparedContext`，即准备好的上下文。它是本次请求的临时视图；下次请求可以根据新的问题重新准备。

Handoff 用于交接工作，需要保存目标、已验证进度、阻塞、下一步及相关证据。PowerContext 支持先准备交接内容，再提交保存。只有提交成功后，接手者才能通过持久引用读取这次交接。

各类产物的用途和保存方式，见 [PowerContext 核心概念](https://github.com/oceanbase/powercontext/blob/powercontext-v1.0.0/docs/zh/docs/get-started/core-concepts.md)。

## 3. 一次请求的上下文工作流程

### 3.1 从工作材料到任务反馈

从保存材料到继续工作，上下文通常经过以下处理。已有资料可以重复使用，因此每次请求不必重新执行全部步骤。

1. 明确当前任务，选择对应的 Scope。
2. 保存相关材料，记录需要复用的决定，或按配置生成产物。
3. 找出相关内容，检查版本、有效状态和访问权限。
4. 在预算内组织上下文，保留引用，并标明哪些内容来自历史记录。
5. 把准备好的内容加入模型请求，让 Agent 结合当前要求开展工作。
6. 检查任务结果，按需要修订记忆或保存交接。

如果你已经使用过 RAG，会对检索资料并放入生成请求的过程比较熟悉。跨会话工作还需要维护进度、版本和失效状态，帮助后续请求识别过时的结论。

### 3.2 先判断相关性，再控制大小

查找订单日报的退款口径时，可以用项目名和退款统计相关术语缩小范围。不同材料适合的检索方式也不同：

| 方式 | 适合的查询 | 需要考虑的限制 |
| --- | --- | --- |
| 全文检索 | 项目名、字段名、规范编号和错误码 | 查询与原文用词不同时，可能漏掉相关内容 |
| 向量检索 | 用不同措辞表达相近的问题 | 需要向量模型，精确标识符仍需核对 |
| 混合检索 | 同时包含业务意图和明确术语 | 需要合并排序信号，并用实际任务检查效果 |

这几种检索方式的实现示例见[《AI 应用的数据层》](../dev/D2%20课程稿：AI%20应用的数据层.md)。

检索是否相关，要结合当前问题判断。同一条发布规范可能适合代码提交任务，却与订单口径无关。搜索结果中的分数可以帮助排序，但分数高并不说明内容更可信。

选入上下文前，还要检查内容是否满足使用条件，这一步称为准入。即使旧口径排在搜索结果第一位，也要确认它是否仍然有效。没有合适的内容时，可以返回空结果；排查时再区分是没有搜到、条目已停用，还是预算不足。

### 3.3 字节预算与 Token 预算分别核对

上下文大小常用两种单位衡量：UTF-8 字节表示文本大小，Token 用于计算模型窗口占用和用量。准备历史资料时，还要给当前指令、用户输入、工具信息和模型输出留下空间。

PowerContext 用 `max_bytes` 限制准备结果的 UTF-8 字节数。在 1.0.0 中，可以设置为 512 到 32768 字节，默认是 8000。内容放不下时，运行时会缩短正文或跳过条目，同时保留引用和历史信息说明。参数详情见 [上下文文本组装文档](https://github.com/oceanbase/powercontext/blob/powercontext-v1.0.0/docs/zh/docs/workflows/prepare-context-text.md)。

字节与 Token 没有固定换算关系，因此调用模型时仍需检查 Token 预算。想要复现某次裁剪，还应记录当时使用的内容版本、排序和预算；资料发生变化后，同一个查询可能得到不同结果。

Skill 数量增加时，也需要控制加载范围。[《多 Skill 给上下文工程带来的麻烦：如何应对 Agent「爆上下文」》](../extra/X2%20多%20Skill%20给上下文工程带来的麻烦：如何应对%20Agent「爆上下文」.md)提供了全量注入与按需加载的对照练习，可以用来观察两种方式的上下文占用。

### 3.4 引用、修订与冲突处理

一条精确引用需要定位到具体内容及其版本。PowerContext 的 Artifact 引用包含产物类别、标识和修订号；Memory 还提供条目级引用，字段名为 `citation`。通过它可以读到被引用时的内容，即使该条目后来已经更新。

退款范围从 7 天改为 14 天时，可以修订原决定，让后续检索采用新内容，同时保留旧版本供核查。这样，检查一份历史报表时，就能知道它当时依据的是哪个口径。

如果两份材料的结论不同，先看它们是什么关系。同一来源明确发布的修订可以替代旧版；来自不同团队的两份说明，则可能适用于不同场景，需要核对范围和决定权限。无法判断时，应保留分歧并请负责人确认，不能仅凭时间较新就覆盖旧结论。

有些产物需要先审核再使用。例如，PowerContext 会把 Experience 和受管理的 Skill 提议放入待审列表。审核者确认后，才形成正式产物。显式 Memory 保存和修订有各自的操作接口，后面的练习会直接使用这些接口。

不再适用的记忆可以停用，使它退出当前检索范围，同时保留历史。需要彻底清理数据时，则要使用相应的删除流程。

### 3.5 历史资料的信任边界

历史记录可以提供依据，但其中的操作要求仍需结合当前指令判断。例如，旧交接写着可以发布报表，而这次用户只要求检查统计口径，Agent 就应完成检查，不应执行发布。

准备上下文时，应保留出处，并明确标注历史内容。负责运行 Agent 的工具，例如 Codex，还要按指令优先级和当前权限处理这些内容。把一段历史文字放到提示词前面或后面，都不会让它自动获得执行授权。

## 4. MCP、Skills 与 Agent Plugins 怎样配合

运行 Agent 的工具称为宿主，Codex 就是其中一种。接入 PowerContext 时，需要让宿主连接外部服务、加载操作指导，并管理相关配置。MCP、Skills 和 Agent Plugins 分别承担这些工作。

| 机制 | 提供什么 | 本节中的作用 |
| --- | --- | --- |
| MCP | 宿主与外部服务之间的能力发现和调用协议 | 让 Agent 发现并调用 PowerContext 的记忆工具 |
| Skills | 以 `SKILL.md` 及相关资源组织的任务指导，供宿主按需发现和加载 | 指导 Agent 何时搜索、保存、修订或交接，以及如何检查结果 |
| Agent Plugins | 将 Skills、MCP 配置和宿主支持的其他组件打包分发 | 一次安装接入操作指导、工具连接及宿主 Hook |

协议和文件格式可以查阅 [MCP 架构说明](https://modelcontextprotocol.io/docs/2026-07-28/learn/architecture)、[Agent Skills 概述](https://agentskills.io/home)和 [OpenAI 插件文档](https://learn.chatgpt.com/docs/plugins#use-plugins-from-a-supported-surface)。它们分别说明服务如何连接、Skill 如何组织，以及 Codex 插件可以包含哪些组件。

实际使用时，插件把工具连接和 Skill 安装到宿主中，MCP 负责传递调用，PowerContext Server 负责保存和读取内容。只有保存请求成功，服务端才有可供后续使用的记忆。

以本节演示的 Codex 集成为例，PowerContext 插件还支持自动召回。你提交提示词时，`UserPromptSubmit` Hook 会请求准备上下文，再把结果交给 Codex。Hook 是在指定事件发生时运行的程序。插件还会在会话启动时通过 `SessionStart` 绑定 Scope，并通过 `PreToolUse` 让工具操作使用同一个 Scope。

更换宿主时，需要核对它支持的插件格式、认证方式和 Hook。PowerContext 提供[可移植 Agent Plugin 包](https://github.com/oceanbase/powercontext/tree/powercontext-v1.0.0/integrations/agent-plugin/powercontext)，可供兼容宿主加载 Skill 和 MCP 配置；自动召回是否可用，还取决于具体集成。

Skill 可以指导不同的任务。订单日报核对 Skill 告诉 Agent 怎样检查业务结果，PowerContext 插件附带的 Skill 则告诉它怎样保存和查找上下文。使用时按任务加载相关指导即可。

如何把操作经验整理成可复用的文档，以及怎样组织和共享这些文档，可以参阅[《Skill 与 Agent 知识管理》](../pm/P4%20课程稿：Skill%20与%20Agent%20知识管理.md)。

## 5. 动手练习：以 Codex 为例接入 PowerContext

下面使用 Codex CLI 演示完整流程。如果你已经在使用其他支持 MCP 和 Skills 的 Agent 工具，也可以按对应的集成文档接入 PowerContext。选择工具时，要确认它能连接服务、加载操作指导，并让前后两个会话访问同一个 Scope；自动召回还取决于宿主是否支持相应的 Hook。

安装命令、环境变量和会话切换操作会随宿主变化。以下具体命令采用 Codex 的用法；换用其他工具后，仍按相同标准检查保存、检索、修订和引用结果。

### 5.1 准备环境

按照下面的 Codex 示例操作，需要准备：

- macOS 或 Linux，以及 Bash 终端。Windows 支持仍处于试验阶段，需要另行核对安装要求。
- Python 3.11+、Git、curl 和 [uv](https://docs.astral.sh/uv/getting-started/installation/)。
- 已安装并登录的 Codex CLI，能够正常对话，并支持插件和 Hooks。本节使用 Codex CLI 0.153.4 验证。可以用 `codex --version` 查看版本，用 `codex plugin --help` 检查插件入口。

下面的命令使用 [PowerContext 1.0.0](https://pypi.org/project/powercontext/1.0.0/) 和对应版本的 Codex 插件。我们会明确要求 Agent 保存和检索 Memory，无需为 PowerContext 另行配置生成或向量模型。你使用的 Agent 工具本身仍需要可用的模型访问。

服务运行在你自己的电脑上，地址为 `127.0.0.1:8000`。示例采用全新的本地配置，不启用鉴权，仅用于本机练习。如果 8000 端口已经被占用，请选用其他端口，并同步替换后续命令中的地址。

练习中的 Aurora 是一个虚构项目，可以直接使用文中的示例数据。安装插件时，PowerContext 会向 Codex 注册插件市场并安装插件。Codex 提示检查插件或 Hook 来源时，请核对后再信任。

请从终端启动 Codex CLI，让下面设置的环境变量传入新进程。如果使用桌面 App，需要单独确认它是否读取了相同配置。

### 5.2 安装并启动 Server

在终端 A 执行：

```bash
uv tool install "powercontext[cli,server]==1.0.0"
mkdir -p ~/powercontext-i6
cd ~/powercontext-i6
export POWERCONTEXT_HOME="$PWD/.powercontext"
powercontext server run --no-env-file --host 127.0.0.1 --port 8000
```

服务启动后，保持终端 A 运行。`POWERCONTEXT_HOME` 将默认数据目录设为练习目录下的 `.powercontext`；`--no-env-file` 表示不自动读取环境文件。终端中已有的环境变量仍然有效，如果以前配置过 PowerContext，请确认数据库和连接设置适合这次练习。

另开终端 B，检查服务状态：

```bash
cd ~/powercontext-i6
export POWERCONTEXT_CLIENT_SERVER_URL=http://127.0.0.1:8000
powercontext --version
powercontext doctor
powercontext ready
powercontext capabilities
```

输出应显示 PowerContext 版本为 1.0.0，服务已经就绪。`capabilities` 会列出当前可用的能力；生成和向量模型未配置不影响本次练习。确认服务正常后，再继续安装插件。

### 5.3 创建独立 Scope

在终端 B 为 Aurora 创建一个独立 Scope。请求中的 `idempotency_key` 用于识别重复请求，避免重复创建同一个练习范围。

```bash
curl --fail --silent --show-error \
  --header 'Content-Type: application/json' \
  --data '{"title":"I6 Aurora lab","summary":"Order report context exercise","idempotency_key":"i6-aurora-lab"}' \
  http://127.0.0.1:8000/v1/scopes
```

服务端会返回 `scope_id`。在 Codex 示例中，复制这个值，替换下面的 `REPLACE_WITH_RETURNED_SCOPE_ID`，然后执行：

```bash
export POWERCONTEXT_CODEX_SCOPE_ID='REPLACE_WITH_RETURNED_SCOPE_ID'
```

Codex 会在会话启动时绑定这个 Scope。后面的两个会话都要连接同一服务，并使用这个 ID，才能共享记忆。换用新终端时，请重新设置变量；如果想从空白数据开始重做练习，可以更换幂等键，创建另一个 Scope。

### 5.4 安装插件，检查 Skill 和 MCP

继续在终端 B 执行：

```bash
powercontext setup codex \
  --ref powercontext-v1.0.0 \
  --server-url http://127.0.0.1:8000
powercontext doctor codex
export POWERCONTEXT_CODEX_CAPTURE_PROMPTS=false
codex
```

`POWERCONTEXT_CODEX_CAPTURE_PROMPTS=false` 关闭了自动提示词采集，方便我们观察明确要求保存的那条记忆。自动召回仍可运行。以后需要采集对话作为 Source 时，可以按 [Codex 集成文档](https://github.com/oceanbase/powercontext/blob/powercontext-v1.0.0/docs/zh/docs/integrations/codex.md)启用相关配置。

`--server-url` 指定插件连接的服务地址。更换端口或服务时，用新地址重新执行 setup，再开启 Codex 会话。MCP 和 Hook 会从插件的同一份配置中读取连接地址。

安装结果中的插件版本可能显示为 0.2.0，这是 `powercontext-v1.0.0` 标签中 Codex 插件自己的版本号。Server 的版本仍应为 1.0.0，两者使用各自的版本编号。

进入 Codex 后，用以下[内置命令](https://learn.chatgpt.com/docs/developer-commands#built-in-slash-commands)检查安装结果：

- `/plugins`：PowerContext 插件已安装并启用。
- `/hooks`：可以找到 `SessionStart`、`UserPromptSubmit` 和 `PreToolUse`。如果首次启动时 Hook 尚未获得信任，请完成信任后退出并重新启动 Codex，让会话绑定正常运行。
- `/mcp`：`powercontext` 已连接，并列出 `remember_memory`、`search_memory`、`get_memory_entry` 和 `revise_memory_entry` 等工具。
- `/skills`：可以找到 PowerContext 的 [`project-context` Skill](https://github.com/oceanbase/powercontext/blob/powercontext-v1.0.0/integrations/codex/plugins/powercontext/skills/project-context/SKILL.md)。这是 1.0.0 插件使用的名称。

请 Codex 读取 `project-context` Skill，并说明保存、搜索和修订记忆各使用什么工具。此时只需阅读操作指导。若缺少 Skill 或工具，可以先按[常见问题](#_7-2-常见问题)排查，再开始写入。

### 5.5 会话 A：显式保存一条决定

先请 Codex 显示当前 `scope_id`，与[创建独立 Scope](#_5-3-创建独立-scope)时记录的 ID 核对。一致后，发送以下请求：

> 请使用 PowerContext 的 project-context Skill，在当前 Scope 保存这条决定：Aurora 订单日报统计最近 7 天的退款。kind 使用 decision，正文使用 `Aurora refund report covers the last 7 days.`。保存成功后，搜索 `Aurora refund report`，展示正文和完整 citation。

保存时，`remember_memory` 使用以下字段，其中占位值应替换为实际 ID。Codex 显示的工具名可能带有命名空间前缀。

```json
{
  "scope_id": "REPLACE_WITH_RETURNED_SCOPE_ID",
  "kind": "decision",
  "text": "Aurora refund report covers the last 7 days."
}
```

查看工具调用记录，确认写入成功，再检查搜索结果。把返回的完整 `citation` 复制到笔记中，后面会用到。它包含 `memory_ref`、`entry_id` 和 `entry_version_id`，请保留服务端返回的值。

练习中，我们直接输入这条决定。在真实项目里，还可以保留对应需求或评审记录，方便以后核对决定的依据。

### 5.6 会话 B：通过 MCP 找回历史

使用 `/quit` 退出会话 A，在同一个终端重新运行 `codex`。这样会创建一个新会话，同时保留之前设置的 Scope 和提示词采集变量。这里需要新会话，请勿使用 `codex resume`。

在新会话中询问退款范围，不在问题里提供答案：

> 请通过 PowerContext 搜索当前 Scope 中的 `Aurora refund report`，mode 使用 auto，limit 使用 3。根据结果说明退款统计范围，并附上完整 citation。如果没有找到，请说明未找到。本次只读取记忆。

对应的 `search_memory` 请求如下：

```json
{
  "scope_id": "REPLACE_WITH_RETURNED_SCOPE_ID",
  "query": "Aurora refund report",
  "mode": "auto",
  "limit": 3
}
```

搜索结果应包含刚保存的 7 天决定，citation 应指向同一条目和版本。把它与笔记中的引用对照，就能确认新会话读到了已保存的数据。

未配置向量模型时，`mode: auto` 在本次练习中使用全文检索，响应中的 `mode` 会显示为 `fts`。查询使用 `Aurora refund report` 这些正文中已有的关键词，便于核对结果。

即使自动 Hook 已经提供了这条信息，也请完成一次显式搜索，以检查 MCP 工具调用。自动召回是否成功，需要另外查看 Hook 的执行结果。

### 5.7 修订决定，再核对旧引用

继续在会话 B 中发送下面的请求，并在末尾粘贴笔记中的完整旧 citation，供 Codex 读取历史版本。

> Aurora 的退款统计范围改为最近 14 天。请先读取当前条目，再用当前 citation 修订这条决定，正文改为 `Aurora refund report covers the last 14 days.`。修订后搜索确认结果，并用我附上的旧 citation 读取历史内容。

检查以下结果：

- Agent 先读取当前条目，再使用 `revise_memory_entry` 提交修订。读取当前条目可以使用 `list_memory_entries`，也可以通过精确 citation 调用 `get_memory_entry`。
- 当前搜索结果为 14 天，条目 ID 保持不变，版本发生变化。
- `get_memory_entry` 使用旧 citation 时仍能读到 7 天。

修订请求中的引用也用于检查并发修改。如果其他人在你读取后改过这条记忆，服务端会发现版本不一致。这时要重新读取当前内容，再决定如何修改。

### 5.8 观察上下文预算

使用 `/quit` 退出 Codex，回到终端 B。保留 Scope 环境变量，执行下面的命令，查看 PowerContext 为这个查询准备了什么内容：

```bash
curl --fail --silent --show-error \
  --header 'Content-Type: application/json' \
  --data "{\"scope_id\":\"$POWERCONTEXT_CODEX_SCOPE_ID\",\"query\":\"Aurora refund report\",\"max_bytes\":8000}" \
  http://127.0.0.1:8000/v1/context/prepare
```

先记录这次响应，再把 `max_bytes` 改为 512，重新执行命令。对照两次结果中的以下字段：

| 字段 | 检查内容 |
| --- | --- |
| `schema` | 是否为 `powercontext.prepared-context.v1` |
| `status` | 有内容时为 `ready`，无可输出内容时为 `empty` |
| `content_bytes` | 是否不超过本次请求的 `max_bytes` |
| `content` | 正文是否保留历史信息说明和精确引用，哪些内容被缩短或省略 |

如果短记忆连同引用等信息在两个预算内都能装下，两次结果可能相同。如果 512 字节连必要结构都放不下，则可能返回 `empty`。观察重点是内容怎样适应预算，以及引用是否完整。

本例在空白环境中的结果是：8000 字节预算返回 `ready`，正文连同引用和历史信息说明占 640 字节；512 字节预算返回 `empty`，`content` 为 `null`，`content_bytes` 为 0。你的结果应以实际响应为准。

这一步把准备结果显示在终端中，还没有送入模型请求。插件自动召回时，会由 Hook 把准备结果交给 Codex；可以通过 Hook 记录继续检查这一过程。

也可以在原练习 Scope 中开启一个新会话，输入 `Aurora refund report 的退款范围？`，观察自动召回。这里先使用简短查询：全文检索对用词敏感，把整段操作要求作为查询时，即使手动搜索能找到记忆，自动召回也可能为空。看到正确回答后，仍要结合 Hook 或会话记录区分它来自自动注入还是显式工具调用。

### 5.9 可选练习：交接当前工作

一条记忆能传递决定，但交接工作还需要说明进度和下一步。在同一终端启动 `codex`，先搜索并读取当前 Memory，再按照下面的模拟状态保存一次交接。

> 请准备并提交 Aurora 订单日报任务的交接。目标是完成报表，退款统计范围已确认为最近 14 天。目前尚未连接数据源，也没有完成报表校验，下一步是核对订单表字段。请关联刚才的记忆引用，并返回保存后的交接引用。

查看 `handoff_current_work` 和 `commit_handoff` 的返回结果，确认交接已准备并提交。复制保存后的引用，在新会话中让 Codex 通过 `continue_handoff` 读取它，检查目标、进度和下一步是否完整。

读取交接后，Codex 应知道数据源尚未连接，报表也没有完成校验。如果它把这些待办事项写成已完成，就需要纠正交接内容或对内容的理解。

## 6. 如何判断上下文帮助了任务

### 6.1 分别检查准备、注入、使用和收益

前面的练习涉及几个不同环节：PowerContext 准备内容，宿主把它加入请求，Agent 根据内容回答问题，最后再看回答是否更好。它们之间的区别可以记为 `Prepared ≠ Injected ≠ Used ≠ Benefited`。

| 阶段 | 需要回答的问题 | 可检查的证据 |
| --- | --- | --- |
| Prepared（已准备） | PowerContext 是否返回了符合预算的上下文 | 准备响应中的正文、大小和引用 |
| Injected（已注入） | 这些内容是否进入了模型请求 | Hook 交付结果、宿主请求记录或注入追踪 |
| Used（已使用） | Agent 是否在回答或操作中采用了这些信息 | 回答使用了正确口径，或操作遵循了对应约束 |
| Benefited（有帮助） | 任务是否因此完成得更好 | 对照任务的正确率、返工次数、耗时和费用 |

检查是否使用了上下文时，要看回答和实际操作。例如，回答虽然附了新版本引用，却仍然说退款范围是 7 天，就没有正确采用这条信息。这样的检查可以发现行为上的问题，但无法直接证明模型内部如何处理了输入。

可以用 Aurora 做一个对照。先按[创建独立 Scope](#_5-3-创建独立-scope)中的步骤创建一个空白 Scope，将名称和幂等键改为新的值，例如 `I6 empty control` 和 `i6-empty-control`。不要给它设置 Parent 或上下文引用，也不要保存 Aurora 的决定。

沿用 Codex 示例时，在一个新终端中，把 `POWERCONTEXT_CODEX_SCOPE_ID` 设为空白 Scope 的 ID，并设置 `POWERCONTEXT_CODEX_CAPTURE_PROMPTS=false`，再启动 Codex。发送[通过 MCP 找回历史](#_5-6-会话-b-通过-mcp-找回历史)中的搜索请求。随后退出，改用原练习 Scope 的 ID，重新启动 Codex，再发送完全相同的请求。两次都不直接给出答案，也不续接旧会话。前者应说明未找到，后者应找到 14 天的决定并提供引用。记录是否需要你补充信息、是否采用旧口径，以及各自的耗时。

这组对照能展示跨会话记忆的作用。要评估它在项目中是否划算，还需要固定模型、任务输入和判断标准，在多组任务上比较结果。费用应采用实际用量，并计入检索、准备和额外模型调用；插件显示的 Token 压缩估计只能作为参考。

### 6.2 找到影响结果的环节

回答不符合预期时，可以沿着信息的处理过程查找原因。如果决定从未保存，调整检索方式也找不回来；如果已经搜到却没放进上下文，就要检查裁剪和注入过程。

| 环节 | 可能的问题 | 优先核对的内容 |
| --- | --- | --- |
| 收集与维护 | 关键决定没有保存，或旧决定仍在使用 | 是否保存了来源，记忆是否已修订或停用 |
| 检索与准入 | 查不到相关条目，或选入无关内容 | 查询词、检索方式、Scope 和条目状态 |
| 装配与注入 | 引用丢失、内容超限，或准备后没有进入请求 | 裁剪后的正文、Hook 记录和实际请求 |

找到原因并调整后，再用原来的任务检查效果。对于订单日报，最终要确认的是统计口径和报表结果是否正确。

### 6.3 在质量、延迟和成本之间取舍

检索、重排、文本装配和网络传输都会消耗时间，使用模型重新排序或生成摘要还会增加调用开销。可以分别记录各环节的耗时，找出等待主要发生在哪里。

频繁发生的简单查询通常不需要很多候选内容，可以先控制检索数量。复杂任务可能需要更多证据和多轮核对，扩大预算后要观察错误是否减少。离线任务允许更长的等待时间，可以进一步比较批量处理的成本。

减少重复输入、按需读取原文，以及利用提供方支持的缓存，都可能降低开销。使用摘要时保留原文引用，以便补查细节；使用缓存时关注实际命中情况，再按完整任务的用量核算费用。

## 7. 检查练习结果

### 7.1 记录结果

保留下面这些结果，可以检查每一步是否完成，也方便遇到问题时定位原因。

| 检查项 | 记录内容 | 预期结果 |
| --- | --- | --- |
| 安装与接入 | Server 版本和状态，插件、Skill、MCP 工具的检查结果 | 服务就绪，Agent 能加载 Skill 并调用工具 |
| 工作范围 | 两个会话使用的 `scope_id` | 同一练习使用相同 Scope |
| 保存与召回 | 写入结果、会话 B 的搜索结果和 citation | 新会话能找回原决定 |
| 修订 | 当前搜索结果和旧 citation 的读取结果 | 当前为 14 天，历史仍为 7 天 |
| 预算 | 8000 与 512 字节两次请求的响应字段 | 输出不超过预算，能解释内容是否发生变化 |
| 上下文效果 | 准备结果、注入记录、Agent 回答和任务对照 | 分别说明观察到了什么，哪些环节还无法判断 |

如果完成了可选交接练习，也请记录交接引用，以及新会话读取到的目标、进度和下一步。

完成所有检查后，还可以要求 Agent 停用那条退款决定。确认当前搜索不再返回该条目，再用旧 citation 检查历史内容是否仍可读取。

停用后，当前条目的 `state` 为 `inactive`。旧引用读取的是当时的快照，其中仍可能显示 `active`；这不代表条目重新进入了当前检索范围。

### 7.2 常见问题

下表中的命令和环境变量沿用 Codex 示例。使用其他宿主时，请检查对应的插件、工具连接和 Scope 配置。

| 现象 | 优先检查 |
| --- | --- |
| 找不到 `powercontext` 命令 | uv 的工具安装目录是否已加入 PATH；重新打开终端后再检查 |
| 插件存在，MCP 无法连接 | Server 是否运行；连接地址、端口和认证是否一致 |
| 有 MCP 工具，找不到 Skill | 插件是否完整加载；重启 Codex 后检查 `/skills` |
| Agent 表示已记住，搜索却为空 | 是否存在成功的写入调用；Scope 是否相同；查询是否包含保存正文中的项目关键词 |
| 两个会话结果不同 | 启动 Codex 前是否设置同一 `POWERCONTEXT_CODEX_SCOPE_ID`；绑定 Hook 是否运行；是否连接同一数据库和 Server |
| 手动搜索正常，自动召回没有内容 | Hook 是否执行，是否连接同一地址和 Scope；准备接口是否返回空结果。未配置向量模型时，整段提示词可能无法匹配英文记忆，可先用 `Aurora refund report` 这样的关键词检查 |
| 启用 Source 采集后，没有生成 Memory | 是否配置了自动提取所需的模型和处理规则；也可以先显式保存记忆 |
| 修订返回冲突 | 是否使用了过时引用；重新读取当前条目后再处理 |

PowerContext 连接失败时，Agent 仍可能正常对话。判断接入是否成功，请查看具体的工具返回和 Hook 记录。

## 8. 从练习扩展到项目

如果任务只有少量材料，直接在应用中组织上下文通常就够用。项目需要跨会话继续、多人共享决定，或经常核对历史依据时，可以考虑把上下文交给独立服务管理。

独立服务也会增加部署和运维工作。可以先检查项目里有多少地方在重复实现来源管理、检索和修订：如果多个 Agent 都需要同一套规则，共享服务能减少重复维护；只有一个简单应用时，则需要权衡引入服务的成本。

接入自己的项目时，可以先选一条需要跨会话复用的决定，完成保存、读取和修订，再按需要加入来源采集、交接或自动提取。每增加一项功能，都用实际任务检查结果。例如，启用自动提取后，要确认生成的记忆有来源依据，并且能在新会话中正确使用。
